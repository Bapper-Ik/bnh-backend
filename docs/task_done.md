## AUD-001 — transactional audit infrastructure

- Schema/migration: `0002`, append-only `custodian.audit_events` and mutable delivery status in `custodian.outbox_items`; restricted actor/event foreign keys.
- Service: `record_event` participates in the caller's transaction and durably queues archive intent. `audited_transaction` rolls back a rejected business operation before separately recording `access.denied.failure`; errors and request bodies are excluded. IDs supplied to this internal service must be from trusted server context.
- Envelope: UUID/time, actor/type, resource/type, entity/department, office, revision/resolution, outcome, correlation, unique event key, policy and digest. Digests are SHA-256 format; changed-field names use a closed vocabulary. Registry rejects duplicate/unknown actions. Domain features populate their applicable snapshots and wire failure recording at their own boundaries.
- Protection: runtime can SELECT/INSERT events, never UPDATE/DELETE/TRUNCATE or disable the trigger. Archive attempts/status updates do not edit events. Audit/outbox failure rolls back business writes. Duplicate concurrent action keys can commit only one transition.
- No public audit-write or generic audit administration endpoint. Read APIs belong to HIS-001. Database/hosting owners remain a separate trust boundary; pending archive intent is not proof of external protected delivery.
- Verification: full backend suite 97 passed; isolated staged feature checkout 24 passed; Ruff, formatting, and mypy passed in both. Feature commit: `feat(AUD-001): complete transactional append-only audit infrastructure`; verified remote `origin/dev` commit `eacfa9a91baee2893c7fc954cf67b1f9c1266df7`.

## IAM-001 — individual authentication and session lifecycle

- Delivery entry point: `app.auth_app:create_app` includes only runtime and authentication. Existing organisation/requisition work remains separately composed by uncommitted `app.main` until its gates pass.
- Accounts: Argon2 password hashes, unique identity/email, active flag, server permissions. `/auth/accounts` requires `staff:manage`, grants no permissions to a new account, and rejects role/permission mass assignment. First-operator CLI serialises bootstrap and validates email.
- Sessions: hashed opaque cookie/CSRF tokens, HttpOnly/SameSite session cookies, secure production configuration; current account checks and account locks serialise sensitive actions with deactivation/revocation. Logout revokes one session; self revoke ends all sessions; staff managers can revoke another account's sessions. Login and fresh-authentication attempts each have persisted five-failure/15-minute throttles.
- Recovery: operator CLI verifies the supplied email and issues a random token only for an active account. Hash-only storage, 30-minute expiry, superseding issuance, single-use consumption under row locks; successful recovery revokes all sessions. Operator must verify the staff member's identity before handoff. The private link file is mode 0600 under ignored `.state/recovery`; token/password never goes into logs or ordinary account responses. No email transport or MFA is claimed.
- Migrations: account/session schema `0003` and recovery schema `0006`. Existing migrations `0004`/`0005` are retained as required historical dependencies because they were already applied to the shared development database; their inclusion is not a claim that organisation/requisition features are complete. No applied migration is rewritten.
- Events: identity.created; auth.signed_in/signed_out/failed/reauthenticated/sessions_revoked/recovery_issued/recovered/recovery_failed. Failure outcomes persist without credentials; audit insertion failure prevents session issuance.
- Verification: Ruff, format check, mypy, full backend suite (109 passed), including distinct identities, malicious extra fields, inactive/expired/revoked sessions, CSRF/origin denial, failed and successful reauthentication, recovery replay/expiry/replacement/concurrent use, and atomic login failure. Isolated staged checkout: 40 tests passed; Ruff, formatting, and mypy passed. Feature commit: `feat(IAM-001): complete individual accounts recovery and session controls`; verified remote `origin/dev` commit `7281cdde792d9cf4bb25354c9d66c3722122a70f`.

## ORG-001 — organisation and appointments

- Delivered assembly: `app.org_app:create_app` adds directory/lifecycle APIs to authentication. Models preserve one person identity across appointments. Migration 0007 adds entity/department code and active state, entity kind, and unique directory codes without replacing existing records.
- Scope: appointments are explicitly per entity, with department scope for HOD only. No implicit holding-company inheritance/group substitution. Names/codes, active membership, matching HOD department, timezone-aware effective dates, and authorisation references are validated. Existing active appointments must be explicitly revoked before replacement, including expired or future appointments still marked active. Secretary and Chairman cannot be the same person in the same entity.
- Controls: staff management, organisation management, and office assignment permissions stay separate; no self-granted offices or self-transfers. Profile PATCH allows name/active only, never role/permission/department mass assignment. Deactivation revokes sessions. Active routing checks current account, membership, entity, department, appointment and dates under database locks.
- History: staff transfers update membership only; an active HOD must be revoked before transfer. Revoke retains the original scheduled dates and authority reference; audit time records revocation. Repeat revoke returns the existing state without a duplicate successful event. No delete endpoint/cascade removes identities, departments, offices or signed snapshots.
- Audit: organisation.created/updated, identity.created/updated, office.assigned/revoked/assignment_failed; rejected business assignments are recorded after rollback with a safe actor/correlation envelope. Assignment metadata includes office and department. Audit failure remains fail-closed.
- Verification: full backend suite 125 passed with Ruff, formatting, and mypy. Sixteen organisation API/database tests cover distinct department heads, self-grant/mass assignment, entity mismatch, Board separation, dates, transfer/revocation, inactive scopes, old-session denial, two independent operators racing, safe failure events, and unchanged synthetic frozen requisition snapshots. Isolated staged checkout passed 56 tests plus Ruff, formatting, and mypy. ## VEN-001 / screen 10 — reusable vendors and beneficiary versions

- Assembly: `app.vendor_app:create_app`; migration 0009 adds entity-scoped vendors, append-only vendor_versions and beneficiary_versions. Mutable vendor pointers use expected-version/row locking; all prior contact/bank records remain immutable under runtime DB grants and triggers. No deletion endpoint or cascading history removal.
- Permissions: current entity membership is required for lookup/read. Any writable staff member may create a vendor in their entity; creator may maintain it. Explicit vendor:update plus vendor:read_sensitive grants allow another authorised maintainer within their own membership scope. Technical organisation/staff permissions alone do not grant vendor bank access. Read-only accounts cannot mutate or see bank data, including for their previously created vendors.
- Privacy/validation: list/search has only id/entity/version/name/registration/completeness, never bank values or bank-version identifiers. Full detail exposes bank data only to its creator or explicitly sensitive-authorised maintainer; otherwise restricted is distinct from unknown. Bank data is a full triple or null; zero-prefixed account numbers remain strings. Phone lists and email formats are validated. All records explicitly remain not_verified.
- Version behaviour: PATCH supplies a complete new version with expected_version. Data is never silently merged by name; duplicate supplier names keep separate IDs. Beneficiary changes create new records and cannot rewrite a frozen requisition snapshot. Historical version retrieval uses the same current scope/privacy checks.
- Audit: vendor.created/updated/beneficiary_created; vendor.update_failed is persisted safely after rollback. Transaction failures cannot leave partial bank/version writes. Concurrency accepts only one of two updates at the same expected version.
- Verification: vendor tests cover lookup privacy, cross-entity detail/history denial, complete/absent bank triples, leading zeroes, phone preservation, duplicate names, literal/paginated search, immutable submitted snapshots, stale and simultaneous updates, readonly denial, and database UPDATE/DELETE/TRUNCATE denial.
